# Реєстр дефектів коду (Code Smells) — UtilityBill

| № | Назва дефекту | Детальний опис та локалізація у коді | Негативний вплив на проєкт |
|---|---|---|---|
| 1 | Primitive Obsession (Одержимість базовими типами) | Послуги зберігаються як `List<string[]>`, а статус рахунку — як число `int` (0, 1, 2, 3). | Відсутність строгової типізації, ризик помилок через некоректні індекси або некоректні рядки. |
| 2 | Duplicated Code (Дублювання коду) | Парсинг елементів рядків `int.Parse` та `decimal.Parse` повторюється у `CalculateTotal` та `BuildReport`. | При зміні структури даних доведеться змінювати код у кількох місцях. |
| 3 | Long Method / Large Class (Великий клас) | Клас `UtilityBill` відповідає і за збереження даних, і за розрахунки, і за валідацію, і за формування текстового звіту. | Порушення принципу єдиної відповідальності (SRP), складність підтримки коду. |
| 4 | Deeply Nested Conditionals (Складні умови) | Метод `IsValid()` містить складний вираз із безліччю операторів `&&`. | Важко читати та тестувати всі граничні випадки. |
| 5 | Magic Numbers (Магічні числа) | Використання констант статусів `0, 1, 2, 3`, порогів знижок `1000`, `5000` та ставок `0.05m`, `0.15m` без описових імен. | Складність розуміння бізнес-логіки новим розробникам. |
| 6 | Feature Envy (Заздрість до чужих даних) | Метод `BuildReport` інтенсивно витягує внутрішні деталі рядків послуг замість використання методів самих об'єктів. | Висока зв'язаність (tight coupling) між логікою звіту та структурою даних. |
| 7 | Dead Code (Закоментований/невикористовуваний код) | Невикористовувані змінні та закоментовані шматки коду в `UtilityBill.cs`. | Засмічення коду та плутанина при читанні. |
| 8 | Shotgun Surgery (Залпова хірургія) | Зміна форматів цін або статусів вимагає одночасного редагування кількох методів. | Підвищений ризик внести регресійні баги. |
